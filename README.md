# ZOOZoo тз

## 1. Цель проекта

Разработать небольшое веб-приложение для управления животными и зонами зоопарка, проверки доступа посетителей, расчёта стоимости билетов и выполнения операций с животными.

**Главная цель — продемонстрировать качественную архитектуру, а не большое количество функций.**

Технологии: **C#, ASP.NET Core Web API, Entity Framework Core, PostgreSQL, простой веб-интерфейс**.


## 2. Модель данных

Основные сущности:

| Сущность | Основные данные |
|---|---|
| `Animal` | Id, Name, SpeciesId, ZoneId, HealthStatus, InteractionAllowed, FoodType, FeedingFrom, FeedingTo, LastFedAt |
| `Species` | Id, Name |
| `Zone` | Id, Name, AccessPolicyCode, InteractionPolicyCode, RequiredAccessLevel, MinVisitorAge, OpenFrom, OpenTo, IsAvailable |
| `Employee` | Id, Name, RoleName, IsAvailable |
| `Visitor` | Id, Name, BirthDate |
| `TicketType` | Id, Code, Name, BasePrice, AccessLevel, PricingStrategyCode |
| `Ticket` | Id, VisitorId, TicketTypeId, ValidFrom, ValidTo, Price, CreatedAt |

Связи:

- Один вид — много животных.
- Одна зона — много животных.
- Один посетитель — много билетов.
- Один тип билета — много билетов.


Не создаём классы Tiger, Keeper, Veterinarian. Различия между объектами будут в данных и правилах, а не наследовании.

## 3. Три основные точки расширения

### Политики доступа

`IAccessPolicy` определяет дополнительные правила доступа в зону. Например, обычная зона и зона с возрастным ограничением.

Новая политика должна подключаться без переписывания основного сценария проверки доступа.

### Политики взаимодействия

`IAnimalInteractionPolicy` определяет, разрешено ли взаимодействие посетителя с животным с учётом условий конкретной зоны.

### Стратегии расчёта цены

`ITicketPricingStrategy` определяет алгоритм расчёта стоимости билета.

Например, обычная цена и детская скидка. Добавление сезонной цены в будущем не должно требовать изменения сценария создания билета.

## 4. Обязательные бизнес-правила

### Проверка доступа

Посетитель получает доступ, если:

1. Существуют посетитель, билет и зона.
2. Билет принадлежит этому посетителю.
3. Билет действителен в указанный момент времени.
4. Зона доступна и открыта.
5. Возраст посетителя соответствует ограничениям.
6. Уровень доступа билета достаточен.
7. Дополнительная политика зоны разрешает проход.

### Проверка взаимодействия

Проверяем:

1. Животное существует и допускает взаимодействие.
2. Состояние животного позволяет контакт.
3. Билет посетителя действителен и даёт доступ к зоне животного.
4. Политика зоны допускает взаимодействие.
5. Посетитель соответствует возрастным ограничениям.
6. Есть доступный сотрудник с необходимыми возможностями для работы с данным видом.

### Выполнение кормления

Проверяем:

1. Животное и сотрудник существуют.
2. Животное находится в допустимом состоянии.
3. Сотрудник доступен.
4. У сотрудника есть возможность animal.feed, совместимая с видом животного.
5. Наступило допустимое время кормления.
6. Животное ещё не кормили в текущий период — для MVP достаточно одного кормления в день.

После успешной проверки сохраняем `LastFedAt`.

Проверки и изменение состояния должны выполняться как единая операция: при отказе данные не меняются.

### Расчёт билета

Application выбирает стратегию ценообразования, рассчитывает стоимость и сохраняет её в `Ticket.Price`. Сохранённая цена не пересчитывается после изменения ценовой политики.

## 5. Use Cases

Реализуем только следующие сценарии:

1. Добавить животное.
2. Переместить животное в другую зону.
3. Создать посетителя.
4. Создать билет с расчётом цены.
5. Проверить доступ посетителя в зону.
6. Проверить возможность взаимодействия с животным.
7. Проверить возможность сотрудника выполнить операцию.
8. Выполнить кормление.

## 6. Минимальный REST API

```text
GET    /api/v1/animals
POST   /api/v1/animals
PATCH  /api/v1/animals/{id}/zone

GET    /api/v1/zones

GET    /api/v1/employees
GET    /api/v1/visitors
POST   /api/v1/visitors

GET    /api/v1/ticket-types
POST   /api/v1/tickets

POST   /api/v1/access/check
POST   /api/v1/interactions/check
POST   /api/v1/feeding
```

Каждый endpoint должен иметь определённый request, response и формат ошибок. Бизнес-логика находится в Controllers, её вызов и координация — в Service.

Для проверки доступа и взаимодействия возвращаем не только `allowed`, но и `reasonCode`, например `AGE_RESTRICTION` или `TICKET_EXPIRED`.

## 7. Интерфейс

Достаточно четырёх рабочих разделов:

- **Животные:** список, добавление, перемещение.
- **Зоны:** список, состояние и ограничения.
- **Билеты:** выбор посетителя и типа билета, создание.
- **Операции:** проверка доступа, проверка взаимодействия, кормление.

## 8. Тестирование

В первую очередь покрываем unit-тестами:

- разрешённый и запрещённый доступ;
- принадлежность и срок действия билета;
- возрастные ограничения;
- запрет взаимодействия с животным;
- отсутствие необходимых возможностей у сотрудника;
- корректный расчёт цены;
- успешное и повторное кормление;
- кормление в недопустимое время.
